# Assistant Profile Architecture

`pi-profile-state.js` exports `PROFILE_ENTRY` and pure `readProfileBinding(manager)` returning `{profileId,sessionId}` or null. It examines all native custom entries, not the current branch, so tree navigation cannot reassign identity. Only one valid marker matching the manager's native ID is accepted; conflicting/malformed matching markers fail closed. A copied marker with a different ID is inert. This is a logical isolation boundary for optional agent memory, not an operating-system sandbox against arbitrary local code.

`pi-profile-registry.js` owns the private revisioned JSON registry and project defaults. It uses validated paths, no-follow descriptor reads with kernel path, BigInt identity/type/size and before/after checks, private atomic replacement, parent descriptor revalidation/directory fsync, an interprocess mutation lock and a synchronous revision comparison inside the lock. Unknown top-level registry keys and existing profile record keys survive edits. Malformed registry data fails closed; it is not silently replaced. `getProfile(id)` is an async saved-record lookup for memory management, not a loaded-worker claim. The registry reserves the native settings mutation slot before any await, exposes `profilesBusy` in activity and participates in maintenance idle/shutdown. It uses native `getAgentDir()`, and the runtime context uses that same identity's native sessions root. Profile-owned data paths are computed by the server, with safe opaque IDs. Cross-project sharing is intentional: the same profile ID can bind sessions in distinct canonical projects.

`pi-session-store.js` captures a new session's selection before writing any prompt, persists it in the native SessionManager, and serializes the saved binding. List projections pin and recheck the native file around Pi's parser, reject replaced files, and process rows sequentially rather than opening all managers at once. A targeted `getSession` parses only the selected session after native discovery; large project lists still incur one native parse per row when profiles are projected. The REST create endpoint distinguishes omission from explicit null. Native branching retains the original tree and appends one new-ID binding. Session import uses Pi's `forkFrom` to preserve the imported tree and old-ID markers; it does not activate them. `pi-agent-threads.js` uses the store's default-selection policy for new task threads; the extension assistant uses explicit no-profile. Existing sessions without markers remain unbound even if a default is later added.

`pi-agent-routes.js` mounts the profile endpoints under the existing access middleware and composes its environment callback after extension-assistant setup. Before worker startup it reopens the exact canonical session, checks the native ID/cwd/binding and resolves current enabled settings. The Supervisor supplies the context only for persistent eligible workers; no-profile workers explicitly remove any inherited profile-context environment. `pi-profile-runtime.js` revalidates the marker, cwd, ID, server-selected roots and registry flags in the managed extension; it snapshots SOUL at session start and appends it with Pi's public `before_agent_start` hook. No SYSTEM.md replacement or separate transcript is used. A private extension notification acknowledges loaded identity and record revision to the Supervisor; the runtime configuration response separates this state from saved data.

For memory integration, lane B can import `readProfileBinding` from `pi-profile-state.js`. The parent's integration mounts B's `mountProfileMemoryRoutes(router,{profiles:{getProfile: async(id)=>record|null},getAgentDir:async()=>canonicalAgentDir,...})` beneath the access middleware and registers B's `registerProfileMemory(pi)` in the managed extension. B must independently validate the native session identity and profile eligibility for every indexing, search, injection, learned-skill discovery, and write operation; this file's environment JSON is not an authorization token. The parent owns the router wiring, source/document manifests, public API index, and integrated deployment checks.

Tests use isolated Pi identity directories and synthetic provider responses. They cover revision conflicts, symlinked registry rejection, legacy sessions, copied/conflicting markers, both native fork paths, import fidelity, same-name projects, extension prompt append and a real RPC worker acknowledgment. Final integrated memory behavior, non-Linux platform tests and deployment are separate acceptance steps.
