# Pivane 开发流程

## 从需求到交付

1. 用 [模块导航](MODULES.md) 找到职责所有者、现有契约和相关测试。确认源码分支、未提交改动，以及运行实例是否使用独立代码快照。
2. 写清改变的行为和影响范围。优先修改职责所有者；新增任务类型同时考虑运行、超时、停止、回收和维护空闲状态。
3. 开发时用有代表性的相关测试获得快速反馈。对协议、并发、身份、持久化和迁移增加行为测试；简单文案或低影响展示调整不必建立只重复实现的测试。
4. 按下表完成交付检查，同步该变化对应的文档。跨平台或外部服务的验证范围如实记录。
5. 提交前检查 diff 和跟踪清单。需要部署时先完成候选、基线比对和备份准备；已有授权覆盖的工作继续执行。公开发布与本机部署是不同操作。

## 验证矩阵

| 变化 | 开发中 | 交付前增加的检查 |
|---|---|---|
| 应用源码、行为或模块边界 | 相关 Node 用例、语法检查 | `npm test`、`npm run check`；相关文档变化再跑文档检查 |
| UI、样式、脚本加载 | 对应浏览器场景 | Chromium 桌面/手机，pageerror、子项宽度、抽屉/附件/tool 状态；涉及连接或线程状态时覆盖迟到事件与重连 |
| 文档文字 | 核对实际行为与链接 | `npm run check:docs`；改变公开清单、文件位置或发行链接时再跑 `npm run pack:trial` |
| 路径、命名兼容、源码发现、打包、安装或维护 | 隔离行为/故障测试 | 完整 Node、语法、文档、`pack:trial` 和相应安装/恢复演练 |
| 依赖、认证、网络边界或发布候选 | 对应测试 | `npm audit --omit=dev`；发布按 [RELEASING.md](RELEASING.md) 验证准确归档 |
| 原生组件 | 目标平台编译和测试 | 源码/binary/manifest 一致性与目标系统实机验证 |

测试必须有独立身份和合成服务。测试通过不代表真实模型、媒体供应商、Safari 或其他系统已验收。不要为了重复获得相同结果而反复执行全套检查；出现新修改、失败或未覆盖问题时再补验。复用结果须对应相同源码、依赖和执行环境；源码结果不能替代冻结归档的独立安装验收。

## Node 测试入口与计时

统一通过 `npm test` 运行，定向与全量执行使用相同的供应商环境凭据过滤和测试 bundle 配置。用例自身仍须创建独立身份与数据目录；运行器不把任意用例变成安全沙箱。

```bash
npm test -- --list
npm test -- test/pi-agent-thread-input.test.js test/pi-agent-threads-limits.test.js
npm test -- --timing
```

- 无文件参数时全量执行；参数为相对仓库根目录的精确 `.test.js` 路径或测试目录，目录递归选择。多个选择取并集、去重并保持统一发现顺序；不支持通配符、任意 Node 参数或仓库外路径。
- `--list` 只列出选中用例文件，不准备 bundle 或执行测试。任何一个选择没有匹配、未知选项或整个发现集合为空都会失败，避免拼写错误变成零测试通过。
- `--timing` 保留 Node TAP 输出、失败和退出码，并追加最慢的至多 10 个文件及 10 个用例/套件。使用 Node 事件中的耗时；旧 Node 没有逐文件 summary 时仅列用例。嵌套耗时重叠，不可相加；文件耗时不含父运行器开销，用例外的准备也不一定进入用例耗时。
- 开发中先跑相关文件；交付按上面的矩阵。不要为了定向运行而绕过环境过滤，也不要在尚未证明用例隔离前提高全量并发。

Node 用例的清理必须先等待网关、worker 和 SQLite 连接关闭，再删除临时目录；Windows 不允许删除仍被打开的数据库。创建恶意符号链接 fixture 的全量测试需要 Windows 的符号链接权限（开发者模式或提升权限的独立测试任务）；应用安装和日常运行不因此要求管理员权限。浏览器与普通权限核心运行另行验证。

## 浏览器与重型专项

`npm test` **不执行** `test/browser/*.cjs` 或 `test/release/*.cjs`；语法检查和打包发现这些文件不代表执行过它们。按 [模块导航](MODULES.md) 选择与改动相关的专项，先阅读脚本的入口、环境参数和清理逻辑：

| 专项 | 运行前要求 | 适用范围 |
|---|---|---|
| 自建随机 loopback 服务、mock API/WS 的浏览器脚本 | 核对脚本自行启动/清理服务，指定本机 Playwright 与 Chromium | 对应 UI、时序与响应式改动 |
| 依赖外部测试 URL 的浏览器脚本 | 显式传入该脚本支持的 URL，目标必须是独立测试服务，真实 worker 使用独立身份 | 对应 HTTP/WS、worker 集成 |
| 发行安装、升级、恢复 | 新临时目录、合成服务、准确归档 SHA256，按 [发行流程](RELEASING.md) | 冻结发行候选及安装/恢复边界 |
| Pi 受管联网更新 | 显式 opt-in，专用隔离环境，不自动升级开发依赖 | 受管更新链专项 |

部分历史脚本仍有固定测试 URL 或浏览器路径；**不得依赖默认 URL，不能只换生产端口当作隔离**。独立服务需分开 Agent、媒体、项目、预约队列等路径，不继承真实供应商认证；测试不能在维护中的真实会话发消息。未核对入口的脚本不要批量执行，helper 也不是独立测试。

例如 `pi-performance.cjs` 与 `pi-startup-performance.cjs` 自建临时服务，支持 `PLAYWRIGHT_MODULE` 和 `CHROMIUM_PATH`，可在准备好本机依赖后逐个运行。它们分别覆盖流式合并/迟到帧和启动/项目发现，不因同属“性能”而重复；只改无关展示时不必全跑，改变对应时序逻辑时必须覆盖。UI 专项继续检查桌面/手机、pageerror、实际宽度、抽屉、附件和工具状态。

## 源码发现与发布

`scripts/source-files.cjs` 统一枚举 server、public、scripts 和各类测试，递归发现功能子目录；排除用户媒体、旧工作台、vendor 自动发现、隐藏目录和备份，并拒绝代码符号链接。字体和第三方资源使用明确清单。内置能力的官方发布内容由 `vendor/manifest.json` 单独登记并逐文件校验，通过同一 `distributionFiles()` 纳入发行和受管快照；上游 Markdown 不作为 Pivane 自有指南进行链接改写。

- `check-syntax.cjs` 使用相同发现规则检查应用、测试及受管 TypeScript 扩展的语法，不声称执行 TypeScript 类型检查。
- `run-tests.cjs` 从统一发现的 `.test.js` 集合选择并串行执行，避免依赖平台 shell 展开；可选的 `test-timing-reporter.cjs` 只报告 Node 事件，不改变执行顺序或失败语义。
- `package-trial.cjs` 和受管 Pi 更新的源码快照使用相同的 `distributionFiles()`，保留各自的字节、描述符、预算和哈希检查。
- 新增独立资产或文件类型时更新明确清单；新增文档更新 `docs/public-files.json`。改变源码目录还要核对 require/import、HTML 脚本入口、静态访问清单和浏览器 fixture。

## 文档责任

| 内容 | 主要维护位置 |
|---|---|
| 用户如何操作、限制和排障 | `docs/` 对应功能指南 |
| REST/WebSocket 字段、错误和并发语义 | API 与对应功能契约 |
| 模块职责、依赖方向和设计理由 | `docs/development/` |
| Agent 每次开发要遵守的核心要求 | 根目录 AGENTS.md，详细说明通过链接引用 |
| 当前机器、运行/源码基线、有效授权 | 私有维护仓库或已忽略的本地资料 |
| 历史验收和交接 | 私有归档；公开仅保留版本相关的去敏摘要 |

删除重复或错误的现行说明；有追溯价值的旧资料移入历史索引并标明适用版本。不要把发布说明中的历史限制改成当前状态，也不要把已失效的临时规则反复加载到 Agent 上下文。

## 约定的修改

规则应说明保护的对象和适用条件。会话事实、文件身份、隐私和执行归属属于正确性边界；验证范围、目录布局和维护流程可以根据证据调整。阶段性规则在条件消失后移出当前入口。调整规则需要同时检查实现、文档和自动化，不能通过删除规则掩盖尚未解决的问题。

对于多 Agent 工作，默认一个工作区同一文件只有一个写入者；需要并行写入时使用独立 Git worktree，并在明确的合入点核对结果。只有用户授权委派时才启动其他 Agent。
