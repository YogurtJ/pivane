# Pivane 开发流程

## 从需求到交付

1. 用 [模块导航](MODULES.md) 找到职责所有者、现有契约和相关测试。确认源码分支、未提交改动，以及运行实例是否使用独立代码快照。
2. 写清改变的行为和影响范围。优先修改职责所有者；新增任务类型同时考虑运行、超时、停止、回收和维护空闲状态。
3. 开发时用有代表性的相关测试获得快速反馈。对协议、并发、身份、持久化和迁移增加行为测试；简单文案或低影响展示调整不必建立只重复实现的测试。
4. 按下表选择覆盖本次改动的测试，同步该变化对应的文档。本机启用只跑相关测试；全量留给公开发布。跨平台或外部服务的验证范围如实记录。
5. 提交前检查 diff 和跟踪清单。需要部署时先完成候选、基线比对和备份准备；已有授权覆盖的工作继续执行。公开发布与本机部署是不同操作。

## 验证矩阵

按改动的**实际行为**选测试，不按文件数、目录或“要部署了”升级。本机部署的目的是尽快看到效果；测试只需覆盖本次改动，数据与执行安全由部署门槛保证。

| 场景 | 要做的验证 |
|---|---|
| 本机部署（开发迭代、启用看效果） | 覆盖本次改动的 Node 用例和浏览器脚本（UI 改动含桌面与手机宽度），加 `npm run check`；改了文档再跑 `npm run check:docs`。共享 UI、全局样式和主题同样只选直接相关及明显相邻的脚本（例如外壳、设置页），**不跑全量**。RPC/worker/会话与并发、鉴权/文件身份、持久化/迁移、依赖/安装等高风险后端，跑对应模块的测试文件和必要的端到端，也不要求全量 |
| 公开发布 | 按 [发布流程](RELEASING.md#验证范围与证据复用) 比较可追溯基线与本次实际变化，执行失效部分并记录有效复用；缺乏基线、广泛变更或无法界定影响时建立相应全量基线。最终记录绑定实际发布包，不因归档 SHA 或候选编号改变就全量重跑 |

只改文档或规则时，核对事实与 `npm run check:docs`，不跑应用测试，也不部署。

| 附加影响（涉及时才做） | 叠加的检查 |
|---|---|
| UI 与连接状态 | pageerror、实际子项宽度、抽屉、附件、草稿与工具状态；涉及线程/连接时覆盖切换、迟到事件和重连 |
| 跨工具/HTTP/WS/持久化链 | 用独立身份、真实装配的服务或受管 RPC 加合成供应商跑受影响的端到端；写入需覆盖失败/不确定、修订冲突及不重放 |
| 公开清单、文件位置、源码发现、打包、安装、路径兼容或维护 | 文档检查、`npm run pack:trial` 及相应安装/更新/恢复演练；迁移另须原生语义与字节校验 |
| 依赖、认证或网络边界 | `npm audit --omit=dev`、实际依赖解析及对应故障测试；依赖升级按 [依赖与上游适配](DEPENDENCIES.md) |
| 原生组件 | 源码/binary/manifest 一致性、目标平台编译和实机验证；不能用浏览器模拟替代 |

全量 Node 与全量浏览器只在公开发布前（或用户明确要求时）运行，不设定期全量，也不因改动属于“共享”或“全局”而在本机部署前补跑。相关测试暴露跨模块回归时，扩大到受影响模块的测试并修复，而不是改跑全量。已知的旧失败不阻塞本机部署，但要在记录里写明，并在发布前处理。

测试必须有独立身份和合成服务，不在维护中的真实会话发送测试消息。测试通过不代表真实模型、媒体供应商、Safari 或其他系统已验收。

## 验证结果复用与失效

测试证据跟着相关内容与执行条件走：同一份实现、依赖和相关测试已验证，提交、换候选目录或静态同步时**不重跑**；相关内容、运行器或环境变化时，只补受影响部分。公开发布同样按 [失效范围与证据复用](RELEASING.md#验证范围与证据复用) 执行，不另设“包SHA变化即全量”的例外。

1. 记录写清：跑了哪些命令和脚本、结果、已知失败及原因。不要求逐项哈希清单或环境快照；涉及依赖、Node/浏览器版本或配置变化时注明即可。
2. 静态同步只需确认部署文件与测试过的文件字节一致，且不依赖尚未部署的后端改动；不必另建“运行版 + 本批文件”组合再测一遍。
3. 候选切换（需要重启）仍核对归档逐文件内容、锁定依赖的实际安装和启动/能力探针；源码阶段已通过的测试直接引用，不在候选目录重跑。
4. 失败、超时、截断日志或未知退出状态不是通过。先查原因并定向修复，不删断言、不放宽超时、不反复重跑到绿；再次遇到同类问题时先按 [执行成本与止损](RELEASING.md#执行成本与止损) 重新评估，不自动升级候选与全量。
5. 依赖审计依赖外部漏洞库：未改依赖/认证/网络的本机批次不需要审计；公开发布必须刷新审计。

**不可省略的部署现场门槛**：重新核对授权、active/previous、运行版修复、源码/候选/服务/配置绑定、当前队列与全局空闲；保留本次备份和完整性检查、只提交一次的票据/执行记录、启动与 HTTP 字节/能力核验。测试减少不授权跳过这些检查，也不允许复用旧票据或不确定的执行。

## Node 测试入口与计时

统一通过 `npm test` 运行，定向与全量执行使用相同的供应商环境凭据过滤和测试 bundle 配置。用例自身仍须创建独立身份与数据目录；运行器不把任意用例变成安全沙箱。

```bash
npm test -- --list
npm test -- test/pi-agent-thread-input.test.js test/pi-agent-threads-limits.test.js
npm test -- --timing
```

- 无文件参数时全量执行；参数为相对仓库根目录的精确 `.test.js` 路径或测试目录，目录递归选择。多个选择取并集、去重并保持统一发现顺序；不支持通配符、任意 Node 参数或仓库外路径。
- `--list` 只列出选中用例文件，不准备 bundle 或执行测试。任何一个选择没有匹配、未知选项或整个发现集合为空都会失败，避免拼写错误变成零测试通过。
- `--timing` 保留 Node TAP 输出、失败和退出码，并追加最慢的至多 10 个文件及 10 个用例/套件。使用 Node 事件中的耗时；旧 Node 没有逐文件 summary 时仅列用例。嵌套耗时重叠，不可相加；文件耗时不含父运行器开销，用例外的准备也不一定进入用例耗时。
- 开发中先跑相关文件；交付按上面的矩阵。不要为了定向运行而绕过环境过滤，也不要在尚未证明用例隔离前提高全量并发。

全量与定向 Node／浏览器入口还移除继承的 `PI_PACKAGE_DIR`、`PI_SUBAGENT_`／`PI_SUBAGENTS_` 元数据及部署用的 `PI_WEB_SECURE_COOKIE`，使目标 SDK 从本地安装读取版本、独立父 fixture 不误加载 child registration，本地 HTTP fixture 也不继承线上 HTTPS Cookie 策略。用例在运行器启动后可明确建立自身 child 配置或 Cookie 策略；原供应商凭据过滤保持。

Node 用例的清理必须先等待网关、worker 和 SQLite 连接关闭，再删除临时目录；Windows 不允许删除仍被打开的数据库。创建恶意符号链接 fixture 的全量测试需要 Windows 的符号链接权限（开发者模式或提升权限的独立测试任务）；应用安装和日常运行不因此要求管理员权限。浏览器与普通权限核心运行另行验证。

## 浏览器与重型专项

`npm test` **不执行** `test/browser/*.cjs` 或 `test/release/*.cjs`；语法检查和打包发现这些文件不代表执行过它们。

```bash
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser -- --list
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser -- test/browser/pi-workbench.cjs
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser
```

- 运行器串行执行会启动 Chromium 的脚本，沿用 `npm test` 的凭据过滤；脚本读取的 `*_URL` 统一指向一个只提供 `public/` 与 vendor 静态资源的 loopback 服务，API/WS 仍由脚本自己 mock。单个脚本超时 5 分钟，失败时输出末尾日志并以非零退出。`CHROMIUM_PATH` 可指定浏览器。
- 开发和本机部署只跑受影响脚本；全量只在公开发布前运行，具体按 [验证矩阵](#验证矩阵)。`--list` 可核对精确脚本清单；运行器不会自动推导影响范围或判断结果能否复用。
- 先用一个相关脚本核对 vendor 挂载、浏览器版本与非秘密环境（尤其 `LANG`/`LC_ALL`、时区、下载名），再批跑。环境修正后按影响补验，不复制整个生产环境，也不把环境差异导致的失败直接忽略。
- 首行带 `pivane-browser: manual` 的脚本需要真实隔离服务或发行归档，运行器不执行：按脚本说明显式传入目标 URL，服务分开 Agent、媒体、项目、预约队列等路径且不继承真实供应商认证。**不得指向维护中的实例或依赖默认端口。** 发行安装、升级与恢复按 [发行流程](RELEASING.md) 使用准确归档；Pi 受管联网更新需显式 opt-in 的专用隔离环境。
- 界面有意改变导致脚本失败时，修正期望并保留其独有场景；不要靠放宽超时或删断言让失败消失。UI 专项继续检查桌面/手机、pageerror、实际宽度、抽屉、附件和工具状态。

## 源码发现与发布

`scripts/source-files.cjs` 统一枚举 server、public、scripts 和各类测试，递归发现功能子目录；排除用户媒体、旧工作台、vendor 自动发现、隐藏目录和备份，并拒绝代码符号链接。字体和第三方资源使用明确清单。内置能力的官方发布内容由 `vendor/manifest.json` 单独登记并逐文件校验，通过同一 `distributionFiles()` 纳入发行和受管快照；上游 Markdown 不作为 Pivane 自有指南进行链接改写。

- `check-syntax.cjs` 使用相同发现规则检查应用、测试及受管 TypeScript 扩展的语法，不声称执行 TypeScript 类型检查。
- `run-tests.cjs` 从统一发现的 `.test.js` 集合选择并串行执行，避免依赖平台 shell 展开；可选的 `test-timing-reporter.cjs` 只报告 Node 事件，不改变执行顺序或失败语义。`run-browser-tests.cjs` 使用同一发现规则选择浏览器脚本。
- `package-trial.cjs` 和受管 Pi 更新的源码快照使用相同的 `distributionFiles()`，保留各自的字节、描述符、预算和哈希检查。
- 新增独立资产或文件类型时更新明确清单；新增文档更新 `docs/public-files.json`。改变源码目录还要核对 require/import、HTML 脚本入口、静态访问清单和浏览器 fixture。

## 文档责任

| 内容 | 主要维护位置 |
|---|---|
| 用户如何操作、限制和排障 | `docs/` 对应功能指南 |
| REST/WebSocket 字段、错误和并发语义 | API 与对应功能契约 |
| 模块职责、依赖方向和设计理由 | `docs/development/` |
| Agent 每次开发要遵守的核心要求 | 根目录 AGENTS.md，详细说明通过链接引用 |
| 当前机器、运行/源码基线、有效授权 | 私有维护仓库或已忽略的本地资料 |
| 历史验收和交接 | 私有归档；公开仅保留版本相关的去敏摘要 |

删除重复或错误的现行说明；有追溯价值的旧资料移入历史索引并标明适用版本。不要把发布说明中的历史限制改成当前状态，也不要把已失效的临时规则反复加载到 Agent 上下文。

## 约定的修改

规则应说明保护的对象和适用条件。会话事实、文件身份、隐私和执行归属属于正确性边界；验证范围、目录布局和维护流程可以根据证据调整。阶段性规则在条件消失后移出当前入口。调整规则需要同时检查实现、文档和自动化，不能通过删除规则掩盖尚未解决的问题。

对于多 Agent 工作，默认一个工作区同一文件只有一个写入者；需要并行写入时使用独立 Git worktree，并在明确的合入点核对结果。只有用户授权委派时才启动其他 Agent。
